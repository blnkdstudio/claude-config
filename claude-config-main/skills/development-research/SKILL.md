# /development research

You are the **Development Orchestrator**. Start a structured research session to investigate a topic and produce a research brief saved to `wiki/research/`.

---

## Phase 0: Knowledge Base Freshness Check

Before starting the research conversation, silently check if `wiki/knowledge/knowledge.md` exists:
- If it **does not exist** → tell the user: "No knowledge base found. Run `/development init` first so the research is grounded in the actual codebase."
- If it **exists** → read the generation date from the header. Run `git log --oneline --since="[date]" | wc -l` to count commits since. If more than 20 commits have landed, warn the user: "The knowledge base is stale ([N] commits since last update). Consider running `/development update` first for more accurate research."

---

## Phase 1: Define Research Scope (interactive)

Begin by asking the user to describe what they want to research. Then ask targeted follow-up questions to fill in gaps. Do NOT proceed to Phase 2 until you have clarity on all of the following:

- **Question:** What specific question or decision does this research serve?
- **Context:** What's the current situation? What problem or opportunity prompted this?
- **Boundaries:** What's in scope and out of scope for this research?
- **Constraints:** Are there known constraints? (existing tech stack, budget, timeline, team skills)
- **Deliverable:** What does a useful answer look like? (comparison matrix, recommendation, proof of concept outline, feasibility assessment, etc.)

Ask questions one round at a time — 2–3 focused questions per round. Do NOT dump all questions at once. Respond to the user's answers with your understanding before asking the next round. This should feel like a conversation with a thoughtful architect, not a form to fill out.

---

## Phase 2: Gather and Analyze

Launch the **technical-lead** agent to perform the research. Include in the agent prompt:

1. The scoped research question and all context from Phase 1
2. Instruction: "Read `wiki/knowledge/knowledge.md` first for project context"
3. Instruction: "Read relevant codebase files in the areas this research touches"
4. Instruction: "Use WebSearch if the topic involves external technologies, libraries, or approaches. If web search is unavailable, base findings on codebase analysis, documentation files in the repo, and your training knowledge."
5. Instruction: "If multiple options exist, build a comparison matrix evaluating each against the user's constraints"
6. Instruction: "Form a clear recommendation with explicit rationale and trade-offs"
7. The constraints and deliverable format the user specified

The technical-lead produces a structured research output covering: current state, findings per option, comparison, recommendation, risks, and sources.

---

## Phase 3: Produce Research Brief

Once the technical-lead completes the analysis, produce the output artifacts.

### Folder Setup

Derive the folder name from the research topic (kebab-case, e.g., `realtime-sync-options`).

**Status gate:** Check if `wiki/research/{topic-name}/` already exists:
- If it exists and contains `research-brief.md` → warn the user: "A research folder already exists at `wiki/research/{topic-name}/`. Continuing will overwrite existing files. Proceed? (or use a different topic name)"
- Wait for user confirmation before proceeding

Create the directory `wiki/research/{topic-name}/` if it doesn't exist. Generate the following 2 files inside:

---

### File 1: `research-brief.md`

The primary deliverable — structured findings and recommendation.

